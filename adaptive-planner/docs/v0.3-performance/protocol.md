# 基准方法

## 数据与配置

- 一张250k、128维JVector图，构建参数与性能目录一致。
- 八种过滤条件等权混合，各使用Holdout固定前1000条查询。
- E/P/O/N/Planner五方案，优化前后各三轮，共240000请求。
- 单线程、热位图；每方法每过滤器预热50次。
- 每轮使用seed=20261119+round打乱8000个请求，五方案采用相同排列；方案顺序按轮次轮转。

预算由历史Tuning确定：三轮平均Strict Recall均达.95时选择成本最低的已测点；无达标点时选择质量最高的点并标记不达标。Planner使用相同的历史目录规则。首次位图构建成本单独保存。

## 计时

`request_ns`为完整API调用的外层墙钟，`api_ns`为内部响应计时，`search_ns`为检索耗时。GT读取、质量复算和CSV写入在正式测量区间外。

混合P99由每轮8000个请求的真实延迟按最近秩法计算；QPS为8000除以批次墙钟。过滤器在混合流中交错，其单独QPS按该过滤器请求耗时之和计算，标为active-wall。三轮结果分别保存，图表展示中位数。

主测调用不传GT，质量在计时后评价，因此在线质量回退次数为0。该口径适合评估没有在线GT的查询服务；带GT的验证和二次E回退成本需另行测量。

## 优化比较

优化前后使用同一图、输入顺序和缓存条件。原ProductExactIndex与MatchedIdExactIndex均通过QueryApi执行。前后阶段固定顺序，结果可能受JIT、温度和后台负载影响。

## 内存

Heap used/committed与GC每秒采样一次。Private、Working Set和System Available分别记录。早期进程采样指向Oracle启动器，仅基线末段起覆盖真实JVM；因此完整前后内存比较采用Heap，Private峰值的基线覆盖不完整。1Hz采样可能漏掉短峰。
